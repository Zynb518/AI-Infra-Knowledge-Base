# 001-日志分析报告器

## 项目级别

中等

## 项目背景

在实际工作中，日志文件通常包含时间、服务名、日志级别、状态码和耗时等信息。手动统计这些内容效率低，也容易遗漏。

本项目要求编写一个 Bash 脚本，读取一份结构固定的日志文件，提取并统计其中的关键信息，最后生成一份易读的分析报告。

## 使用到的知识

~~~text
Linux 与操作系统
└── 基础使用
    ├── 常用命令与文本处理
    └── Bash 脚本
~~~

预计会使用以下已经学过的知识：

- Bash 脚本文件与执行方式。
- 变量、引用、位置参数和用户输入。
- 命令替换与退出状态。
- 条件判断、循环、数组和函数。
- 重定向、管道、临时文件和清理。
- bash -n、bash -x、标准错误和退出状态。
- grep、cut、wc、sort、uniq、tee 等文本处理命令。

项目实现不得依赖尚未学习的核心知识。如果发现确实需要新的知识，应先暂停项目并单独学习该知识。

## 输入格式

日志文件每行是一条记录，字段使用英文逗号分隔，字段顺序固定为：

~~~text
timestamp,service,level,status,latency_ms
~~~

示例数据：

~~~text
2026-09-22T10:00:01,api,INFO,200,120
2026-09-22T10:00:02,worker,INFO,200,45
2026-09-22T10:00:03,api,ERROR,500,310
2026-09-22T10:00:04,api,INFO,200,98
2026-09-22T10:00:05,database,ERROR,503,420
2026-09-22T10:00:06,worker,INFO,200,52
~~~

字段含义：

| 字段 | 含义 |
| --- | --- |
| timestamp | 日志时间 |
| service | 服务名称 |
| level | 日志级别 |
| status | HTTP 或服务状态码 |
| latency_ms | 请求耗时，单位为毫秒 |

项目第一阶段可以假设输入文件格式正确；空行可以忽略。

## 项目要求

创建一个命令行脚本，至少满足以下要求：

1. 接收日志文件路径作为命令行参数。
2. 没有提供路径时，向标准错误输出错误信息，并返回非零退出状态。
3. 输入文件不存在时，向标准错误输出错误信息，并返回非零退出状态。
4. 读取日志文件，不修改原始日志。
5. 统计日志总记录数。
6. 统计每个服务出现的次数。
7. 统计每种状态码出现的次数。
8. 统计 ERROR 日志数量。
9. 将分析结果写入报告文件。
10. 同时在终端显示报告或报告生成位置。
11. 使用函数拆分至少两个具有独立职责的处理步骤。
12. 对临时文件使用 mktemp，并在脚本退出时清理。
13. 脚本出现输入错误时返回非零状态。

报告的具体排版由学生设计，但必须让读者能够清楚看到总记录数、服务统计、状态码统计和错误数量。

## 建议的命令行形式

项目可以支持下面的基本调用形式：

~~~bash
bash log-analyzer.sh sample.log
~~~

报告文件的位置可以由学生设计，也可以允许通过第二个参数指定。无论采用哪种方式，都要在 README 或脚本帮助信息中说明。

## 限制条件

- 不修改输入日志文件。
- 不把所有处理逻辑写成一条过长命令。
- 至少使用函数组织处理流程。
- 变量作为命令参数时使用双引号。
- 正常报告写入标准输出或报告文件，错误信息写入标准错误。
- 临时文件必须使用 mktemp 创建，并在退出时清理。
- 不使用尚未学习的核心命令或语言特性替代基础练习。

## 验收标准

项目完成后，至少验证以下情况：

1. 使用示例日志可以生成正确的总记录数。
2. 服务统计结果正确，重复服务能够累计。
3. 状态码统计结果正确。
4. ERROR 数量正确。
5. 不提供参数时能提示错误并返回非零状态。
6. 输入文件不存在时能提示错误并返回非零状态。
7. 包含空行的日志不会导致脚本异常。
8. 报告内容和终端提示清晰可读。
9. 使用 bash -n 检查语法通过。
10. 使用 bash -x 检查关键处理流程时，能够看懂主要命令和变量变化。
11. 脚本结束后，自己创建的临时文件已经清理。
